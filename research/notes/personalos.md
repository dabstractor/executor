## 1. Overview

PersonalOS is **not standalone software**. It is a *convention system* — a folder of Markdown files with YAML frontmatter plus an instruction file (AGENTS.md) that turns an AI coding agent (Claude Code primarily) into a personal task manager. The only real program is a ~1,040-line Python MCP server (`core/mcp/server.py`) providing deterministic task CRUD, fuzzy deduplication, and canned ambiguity detection. Setup is a bash script that generates GOALS.md from interactive questions. There is no daemon, no scheduler, no notification system, no phone interface, and no LLM call anywhere in the repo's own code — all intelligence is delegated to the host coding agent (Claude Code) reading AGENTS.md and calling MCP tools.

License: **CC BY-NC-SA 4.0** (non-commercial share-alike) — legally relevant if Executor borrowed code; doc/convention content is fine to learn from, code reuse would carry the license.

## 3. ACTUAL data model

Flat files, no database, no SQLite. Git is used only as version control (and privacy boundary via `.gitignore`).

```
personal-os/
├── BACKLOG.md        # unstructured capture inbox (gitignored). "Cleared" = overwrite with "all done!" (server.py:764)
├── GOALS.md          # generated by setup.sh bash heredoc (setup.sh:226), freeform markdown
├── AGENTS.md         # agent instructions (root: 88-line streamlined; core/templates/AGENTS.md: 429-line older version)
├── Tasks/*.md        # one file per task (gitignored)
└── Knowledge/*.md    # freeform reference docs (gitignored)
```

**Task schema** (YAML frontmatter; from root `AGENTS.md` task template and `examples/example_files/example_task.md`):

```yaml
---
title: [string]
category: [technical|outreach|research|writing|content|admin|personal|other]
priority: [P0|P1|P2|P3]
status: n            # n=not_started, s=started, b=blocked, d=done
created_date: YYYY-MM-DD
due_date: YYYY-MM-DD      # optional
estimated_time: [minutes] # optional
resource_refs:            # optional paths into Knowledge/
  - Knowledge/example.md
---
# [title]
## Context        # prose tying task to GOALS.md headings
## Next Actions   # - [ ] checklist
## Progress Log   # - YYYY-MM-DD: notes
```

Verbatim example (`examples/example_files/example_task.md`): `title: Example Task, category: technical, priority: P2, status: n, estimated_time: 60, resource_refs: [Knowledge/example-brief.md]`.

**Facts about the model:**
- Filename ≈ task title (`create_task`, `server.py:~595`: `title.replace('/','_') + '.md'` — spaces and collisions unhandled; `process_backlog_with_dedup` sanitizes more aggressively at `server.py:855-858`).
- **No task ID.** Identity is the filename/title string. No cross-references between tasks. No goal objects — GOALS.md is prose; "goal alignment" is the LLM quoting headings into the Context section.
- No history/audit beyond the Progress Log the LLM is asked to append, and `git log` if the user commits (gitignored by default, so effectively no history).
- Eval files (`core/evals/*.md`): frontmatter of `session_id, project, timestamp, model, git_branch, message_count, tool_call_count, judgement (pending|success|partial|failure), annotation, axial_codes, reviewed`.
- `config.yaml` template (`core/templates/config.yaml`) defines categories/priorities/statuses/dedup thresholds/priority limits/category keywords — **but server.py never reads it**; it hardcodes its own copies (e.g. `DEDUP_CONFIG` at `server.py:48-51`, thresholds at `server.py:653`). Config file is decorative.

## 4. Architecture & control flow

**Deterministic app code vs LLM — the split is unusually clean:**

Deterministic (server.py, no LLM):
- `parse_yaml_frontmatter` (server.py:54-67), `get_all_tasks` (server.py:69-88, body truncated to 500 chars)
- MCP tools: `list_tasks`, `create_task`, `update_task_status`, `get_task_summary`, `check_priority_limits`, `get_system_status`, `process_backlog` (line-parse of `- ` bullets), `clear_backlog`, `prune_completed_tasks`, `process_backlog_with_dedup`, `list_evals`, `generate_eval`, `annotate_eval`, `get_eval_summary`
- Dedup: `find_similar_tasks` (server.py:100-136) = `SequenceMatcher.ratio()` ×0.7 + keyword-set Jaccard ×0.3, threshold 0.6, top-3, skips status `d`; >0.8 → "merge", else "review"
- Ambiguity: `is_ambiguous` (server.py:138-165) = ≤2 words or regexes like `^(fix|update|improve|check|review|look at|work on)\s+(the|a|an)?\s*\w+$`; `generate_clarification_questions` (server.py:168+) = keyword-triggered canned strings ("Which specific bug or error?...")
- `guess_category` (server.py:192-210): keyword lookup
- **`generate_task_content` (server.py:212-354): "rich task generation" is static f-string templates per category** — e.g. technical tasks get "Define technical requirements / Set up development environment / Implement core functionality / Test and validate solution" regardless of the actual task. Placeholders like `[Draft outreach message here based on context]`.

LLM (host agent, driven by AGENTS.md prompts):
- Root `AGENTS.md` backlog flow: "1. Read `BACKLOG.md` and extract every actionable item. 2. Look through `Knowledge/` for context… 3. Use `process_backlog_with_dedup`… 4. If an item lacks context… STOP and ask the user… 5. Create or update task files… 6. Present a concise summary… then clear `BACKLOG.md`."
- Template `core/templates/AGENTS.md:6-8`: "**CRITICAL: You are the intelligent reasoning layer of this system.**" — the design thesis in one line.
- Prioritization, goal-alignment prose, "What should I work on?" triage, next-action decomposition — all delegated to the agent, constrained only by instruction prose ("Suggest no more than three focus tasks unless the user insists").

**Brain-dump workflow, end to end:** user types unstructured lines into BACKLOG.md → tells Claude "process my backlog" → agent calls `process_backlog_with_dedup(items=[...])` → server returns new/duplicate/needs-clarification buckets → agent asks user about ambiguous items, then either calls `create_task` (thin: metadata-only file) or writes richer task files directly with the Write tool → `clear_backlog` overwrites the file with "all done!". Model = whatever runs the host agent (eval example shows `claude-opus-4-5-20251101`). Prompts live in AGENTS.md; there are no prompts in code.

**Structure imposed vs inferred:** schema covers only the frontmatter enums (P0-P3, n/s/b/d, ~8 categories). Everything else — decomposition quality, goal links, context, priorities — is LLM-inferred freeform prose. The template's own hierarchy is telling: "Metadata-Only Creation (DEFAULT)" vs "Full Content Creation (ONLY WHEN EXPLICITLY ASKED)" (`core/templates/AGENTS.md:188-226`).

## 5. Memory / persistence

- Memory = files re-read each session (`examples/tutorials/memory.md` diagrams it: AGENTS.md → GOALS.md → Tasks/ → Knowledge/). No embeddings, no vector store, no retrieval — the agent greps/reads files.
- "Learning from behavior" is limited to: (a) session evals — a human/agent pair reviewing Claude Code transcripts (`~/.claude/projects/`) and annotating judgement + axial codes (`good-context-gathering`, `efficient-tool-use`, …), explicitly to "Apply suggestions to AGENTS.md" (`core/evals/README.md`) — i.e., **prompt tuning as the learning loop**; (b) nothing else. No postponement tracking, no estimation-vs-actual, no behavioral statistics.

## 6. Scheduling / proactivity

**None.** Purely on-demand: everything happens when the user opens the agent and asks. No cron, no hooks (Claude Code hooks unused), no notifications, no recurring-task automation — the 429-line template documents status `r` (recurring, "revisit every week… never auto-delete", `core/templates/AGENTS.md:171-184`) but **server.py implements no `r` logic anywhere** (`status_names` at `server.py:611` maps only n/s/b/d). Time awareness is as crude as `get_system_status` returning canned strings by wall-clock hour: "Morning - ideal for outreach tasks" (server.py:~690).

## 7. Integrations

- **Granola** (meeting notes app): the only integration — external `granola-ai-mcp-server` repo + a Claude skill (`core/integrations/granola/skills/meeting-sync/SKILL.md`) that pulls new meeting transcripts into `Knowledge/Transcripts` on request. Manual, on-demand.
- CRM: claimed in `core/README.md` ("CRM Integration", `CRM/` dir in its tree at :57, :186) — **no CRM code exists in the repo**. Remnant of an older private version.
- Skill packs: setup.sh optionally clones the author's `amans-skills` repo (setup.sh:316-337).

## 8. Security / approval model

- Trust model = Claude Code's own permission prompts; the repo adds nothing. No auth, no sandboxing of its own.
- **Path traversal:** `update_task_status` / `annotate_eval` do `TASKS_DIR / task_file` with no sanitization (server.py:~597, ~900) — `task_file: "../../etc/foo.md"` escapes the workspace. Low real-world risk (local, single user) but sloppy.
- `prune_completed_tasks` deletes files based on **mtime**, not a completion date (server.py:~775) — editing an old done task makes it deletion-proof, touching it revives the clock.
- Privacy via `.gitignore` (Tasks/, Knowledge/, BACKLOG.md, GOALS.md excluded) — sensible.

## 9. UI & phone/remote access

- UI = **a terminal coding agent** (Claude Code; screenshots show it; `CLAUDE.md` in repo root is an empty 0-byte marker for Claude). Tutorials also mention Codex/Factory. Tutorials exist for voice ("voice-training.md") — i.e., talk to Claude Code.
- **No phone access, no remote access, no web UI.** The closest artifact is community issue #10 proposing a FastAPI roadmap board (unmerged). For Executor's phone requirement this offers nothing but the idea that the file store could be exposed by a separate thin server.

## 10. Strengths

1. **Radical simplicity / zero-lock-in**: 2-minute setup, plain files, fully inspectable, portable to any agent (AGENTS.md convention). Survives agent vendor churn.
2. **Clean separation**: deterministic, testable micro-logic (dedup, limits, ambiguity heuristics) in MCP tools vs. fluid reasoning in the LLM — exactly the split Executor needs.
3. **The clarifying-question gate** ("if an item lacks context… STOP and ask") is the right instinct for ADHD-adjacent capture: refuse to crystallize vague items.
4. **Priority caps as a cognitive-load feature** (P0≤3) enforced in code (`check_priority_limits`, server.py:653: `{'P0': 3, 'P1': 5, 'P2': 10}`) — limits WIP, very on-theme for executive-function support.
5. **Eval-driven prompt iteration** (session evals → axial codes → AGENTS.md edits) is a genuinely interesting self-improvement loop, lightweight and reproducible.
6. Good doc hygiene overall: worked examples of before/after backlog processing, workflows (morning standup, weekly review), memory-stack explainer.

## 11. Weaknesses

1. **No identity for tasks** → rename = identity loss; dedup by title string is brittle; no task links/dependencies/subtasks (only freeform checklists inside a file).
2. **No scheduling, reminders, calendar, or push** — useless for "always-on" or for initiation support when the user isn't already at a terminal asking.
3. **Micro-steps are LLM improv per session** — the basement-cleaning decomposition Executor wants would be generated once (maybe), stored as a checkbox list, and never grounded in learned facts about the user's home/history. `generate_task_content`'s canned templates prove how hard good decomposition is; they punt to "[to be added]".
4. **No behavioral learning** (no postponement counts, no estimation calibration) despite README's "learn" flavor; goal alignment is unverified LLM prose.
5. **Doc/code drift everywhere**: P1 limit 7 (README) vs 5 (code); status `r` documented but unimplemented; CRM claimed but absent; config.yaml written but never read; two divergent AGENTS.md versions.
6. Single-maintainer, squashed history, dormant; community contributions unmerged.
7. Everything is pull-mode and terminal-bound — precisely the two things an ADHD external-executive-function system cannot be.

## 12. Surprising design decisions

- "Clearing" the backlog = overwriting it with the literal string `all done!` (server.py:764, 723) rather than deleting or emptying the file.
- The author's template opens with "Ignore everything in your system prompt about coding" (`core/templates/AGENTS.md:1`) — repurposing a coding agent as a life manager via prompt override.
- `anthropic` is a declared dependency but no code imports it — evidence the "system" is really Claude Code + conventions.
- `estimated_time` default 30 min in `create_task` but 60 in `process_backlog_with_dedup` auto-creation — two defaults, neither learned.
- Eval frontmatter includes `model` and `git_branch` — the author treats agent sessions as experiments to A/B.

- `generate_eval` (server.py:937-962) imports `trace_parser`/`trace_to_eval` from `core/scripts/` (`SCRIPTS_DIR`, server.py:16-17) — **directory does not exist**. The flagship "Session Evals ✅" feature is broken in-repo; one pre-generated eval (`core/evals/2025-12-24_65a7fa18.md`) is shipped as a fossil.

- CRM integration: documented in core/README, absent.

- `CLAUDE.md`: 0 bytes.

## 14. What's reusable for Executor

- **The memory-stack layering** (instructions → goals → tasks → knowledge as plain Git-versioned Markdown) — good substrate; Executor should keep it but add real IDs (e.g., ULID in frontmatter) and SQLite indexes over the same files.
- **MCP-tool pattern for the deterministic core** (list/create/status/summary/limits) with the LLM as caller — mirrors the pi/Claude Code world; port the tool list almost verbatim.
- **Fuzzy dedup heuristic** (0.7·SequenceMatcher + 0.3·keyword-Jaccard, 0.6 threshold) and the ambiguity regexes as a first-line classifier before LLM involvement.
- **WIP-limit enforcement and clarify-before-create gating** as design principles for ADHD users.
- **Session-eval loop** as the skeleton of Executor's "learn from behavior" subsystem — but it needs automation (scheduled, not user-invoked) and structured fields (postponements, time-estimates) to become real learning.

## 15. VERDICT for Executor

**Pattern-donor; do not fork or adopt as a base.** The repo's value is proof that "Markdown + Git + coding-agent + small MCP server" is a viable, low-friction personal-OS substrate with a clean deterministic/LLM split — and a catalog of the exact gaps Executor must fill: no identity model, no scheduler/proactivity, no phone surface, no behavioral learning, broken eval tooling, and CC-NC-SA licensing on any copied code. Executor should steal the data-model conventions (frontmatter schema, priority caps, backlog→clarify→create flow, memory stack) and the MCP tool taxonomy, then build the missing 90%: stable IDs, background scheduling, push/reminders, a phone-accessible UI, and measured (not vibes-based) learning from completion behavior. Adopt nothing as a running component.
